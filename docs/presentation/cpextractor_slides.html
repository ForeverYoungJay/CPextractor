Motivation
Why This Project Exists

Crystal plasticity parameters are valuable, but buried in heterogeneous papers.

  • Parameters appear across prose, tables, supplementary files, and model descriptions, not in a clean machine-readable format.
  • Simple extraction is not enough because scientific reuse requires normalization, provenance, uncertainty, and evidence traceability.
  • Manual curation does not scale well when the goal is retrieval, question answering, and comparative materials analysis.
  • CPextractor treats the task as a full curation workflow, not only as an information extraction model.

System View
End-to-End Architecture

The project links acquisition, extraction, validation, storage, and retrieval in one pipeline.

Inputs Scopus, DOI lists, local full text

Candidate papers are collected from search, manual configuration, or existing local full-text folders.

Parsing Elsevier XML to evidence assets

Each paper becomes `paper.xml`, `sections/*.md`, `tables/*.md`, and `references.json`.

Extraction Two-stage LLM extraction

The model first picks relevant files, then fills a crystal-plasticity schema.

↓
Postprocess Normalization and binding

Units, provenance, references, material conditions, and mechanism scope are resolved deterministically.

Trust Grounding and multi-agent QA

Claims are tied back to spans or table cells, then reviewed by evidence, normalization, consistency, and meta judges.

Outputs Database, review queue, chatbot

Structured records, embeddings, audits, and searchable claims are served to downstream tools.

Trust Stack
Why The Output Is Reviewable

Quality control is layered so confidence comes from evidence, not one model score.

Layer 1: Rules

Schema completeness, unit sanity, provenance conflicts, and physics-aware consistency checks.

Layer 2: Grounding

Claims are mapped to files, character spans, line spans, and table cells as reusable evidence objects.

Layer 3: Judges

Evidence, normalization, consistency, and meta judges assess scientific support and extraction reliability.

Layer 4: Fusion

Rule scores and judge outputs become calibrated document confidence and quality tiers.

Result

The system can block low-quality papers from formal ingest while still keeping audit artifacts for manual review and later recovery.

Data Model
What The System Stores

The core design moves from raw extracted records to reusable, publication-grade claims.

Registry `parameters.registry`

One extracted record per parameter mention with normalized identity, values, scope, provenance, and confidence.

Evidence `evidence_objects`

Reusable local evidence spans and table-cell references for traceability and later retrieval.

Claims `parameter_claims`

The smallest trusted unit for review, auditing, database ingest, and downstream analytics.

Database + Retrieval
How The Outputs Are Used

The same pipeline supports curation, retrieval, and evidence-grounded chatbot answers.

Structured tables

`papers`, `extractions`, `references`, and claim-aware tables organize curated scientific content for downstream use.

Vector layers

`chunks` and `parameter_vectors` allow semantic retrieval over full text and over parameter-level scientific statements.

Evaluation tables

`pipeline_runs`, `evaluation_runs`, `parameter_audits`, and summaries preserve model behavior and review evidence.

Hybrid retrieval in the chatbot

`chatbot.py` combines vector retrieval over chunks, vector retrieval over parameter claims, and structured SQL search over extracted JSON. The answer model is instructed to respond only from the supplied evidence.

This gives the project a clear path from extraction to user-facing scientific QA.

Evaluation
How To Measure Success

The evaluation framework is already set up around three complementary questions.

A

Extraction correctness

Field precision/recall, numeric accuracy, unit normalization, provenance completeness.

B

Judge correctness

Brier score, ECE, wrong-at-high-confidence, agreement with reviewed annotations.

C

Database utility

Retrieval hit rate, QA grounding rate, analyst query success, downstream analytics consistency.

Practical message for the presentation

The project is not only asking “did the model parse a number correctly?” It also asks whether the curated result is trustworthy enough to ingest, searchable enough to retrieve, and grounded enough to support a scientific answer.

Evaluation scripts are organized under `scripts/eval/`

Impact
What This Enables

CPextractor can be positioned as both an extraction system and a curation infrastructure.

  • Build a reusable crystal plasticity parameter database without manually transcribing every paper.
  • Support evidence-grounded RAG so answers can cite exact text spans or table cells.
  • Create analyst workflows for comparison across materials, phases, mechanisms, and loading conditions.
  • Generate review packets and audit trails that make human-in-the-loop correction tractable.

Database paper angle

Focus on curation, provenance, quality tiers, retrieval, and reusable scientific infrastructure.

Information extraction paper angle

Focus on file selection, scientific schema extraction, grounding, and evaluation under uncertainty.

Demo angle

Show one paper becoming claims, audits, DB records, and a chatbot answer backed by evidence.

This dual positioning is stated directly in `docs/methods_workflow.md`
